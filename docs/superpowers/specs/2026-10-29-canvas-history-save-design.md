# M1.3：可撤销布局与可信保存设计

日期：2026-10-29。状态：维护者已在当前会话确认，开始分批实施。承接 [长期计划 M1.3](../plans/2026-10-29-long-term-development.md) 与 [输入和浏览器验证](../../verification/2026-10-29-canvas-input.md)。首批实施为独立历史模型，数据库和保存界面尚未改变。

## 目标与范围

一次拖动对应一次可撤销布局命令。保存失败保留眼前布局，显示明确的重试入口；旧请求或其他标签页不能静默覆盖更新的布局。沿用 React + Express + MySQL、现有所有权与图片鉴权，不引入画布 SDK 或新依赖。

首批命令只覆盖 `/journal/layout` 支持的照片、文字/贴纸和记录卡位置、旋转，以及现有照片组的刚性移动。照片组的一次移动是一个批量命令，不拆成多条历史。手帐封面位置走独立接口，首批保持现状，不显示为可撤销操作。

不包括删除、导入、备份还原、组结构修改、折叠/展开、手帐页排版、相机位置或富文本撤销；不承诺离线双向同步或跨标签页合并。不改变当前碰撞避让或拖动取消规则。

## 使用者看见的行为

- 工具栏增加撤销、重做及保存状态，按钮可用状态与快捷键一致。快捷键 Ctrl/Cmd+Z、Ctrl/Cmd+Shift+Z；不拦截编辑器自身历史、输入法、其他区域或打开的弹窗。
- pointermove 只改变预览；正常松手后，把最终碰撞规划得到的位置记录为一个命令。Escape、pointercancel、失焦不增加历史、不写服务端。
- 状态明确区分“未保存 / 保存中 / 已保存 / 保存失败”。已保存只表示当前布局已取得服务端确认。失败后布局不跳回旧位置，显示“重试保存”；重试保存当前意图，不重新播放拖动。
- 保存中仍沿用现有交互锁，避免本阶段扩大并发编辑范围。失败后可以继续排版或撤销，但不会自动继续发送请求；用户点击重试才提交合并后的当前布局。
- 正常连续拖动可以逐次撤销与重做。新编辑截断重做分支；历史最多 100 条命令。刷新不保留历史；存在未确认编辑时，浏览器离开提示生效，不能宣称已保存草稿。

## 布局命令与历史模型

新增 `src/journal/canvas/history.js`，提供不依赖 React/网络的纯状态变换。命令为 `{ id, before, after }`，before/after 是同一组 `{ kind, id, x, y, rotation }`；键使用 kind+id。id 只用于客户端历史识别，不作为服务端幂等凭据。去除没有位置/旋转变化的对象，空命令不入栈；上限沿用 API 的 500 项。

before 来自手势开始时的模型，after 来自松手后的实际碰撞规划；不从 pointermove 的 DOM 回读。普通记录卡坐标继续使用已有 anchor 相对约定，标注与照片使用现有接口约定。首次移动旧的相对定位照片会固定为绝对位置；撤销恢复其视觉起点，保持绝对定位，不承诺恢复原来的旅程跟随语义。

撤销/重做先计算目标布局，再走统一的布局编辑入口；不直接修改 DOM 或绕过保存协调器。组移动保留全部成员相对位置及旋转。历史和服务端确认是两件事：撤销已保存动作会产生新的版本写入，不把历史游标当作数据库版本。

## 服务端版本与重试协议

单纯前端串行队列只能处理响应顺序，无法阻止超时的旧事务晚于新事务提交。因此在接入“保留失败编辑”之前先实现版本协议。

1. 为 `journal_photos`、`journal_entries`、`journal_marks` 增加 `layout_version BIGINT UNSIGNED NOT NULL DEFAULT 0`，追加式显式迁移；不在服务启动时自动改表。GET journal 返回版本的十进制字符串，前端不转 Number。
2. 新布局请求使用 `{ expected_structure_version, items: [{ id, kind, x, y, rotation, expected_version }] }`。一次请求必须全部携带版本或全部不带，拒绝混用及重复 kind+id；旧接口限额、坐标/旋转校验和所有权规则保留。
3. 按 kind+id 的确定顺序锁定所有对象，先检查所有权和版本，再统一写入；任何缺失、非法或冲突均不部分写入。成功更新每行版本 +1，返回 `{ saved, items: [{ id, kind, layout_version }] }`。
4. 重试必须原样重发尚未确认的那一份请求，包括 expected_version。若所有行均是 expected_version+1，且坐标/旋转与请求完全一致（照片还必须已经是 canvas_absolute=TRUE），则视为同值重试并返回当前版本，不再次增加版本。若有部分匹配或任意不同值，返回 409 `LAYOUT_CONFLICT`，不写入。不能用浮点近似比较绕过冲突。
5. 无版本旧客户端仍可写入，但成功后也递增版本；不承诺旧客户端之间的并发保护。新客户端遇到它修改的对象会得到冲突，要求重新载入。文档明确升级时关闭旧页面。
6. 盘点并更新所有其他坐标写入口：分组展开/保存、批量照片信息、记录/标注编辑、自动避让修复等。新版调用必须提供所涉及对象的 expected_version 和 expected_structure_version，在同一事务中先比较再写入，改变坐标/旋转时递增对应行版本；不能只递增而不比较。旧客户端的无条件写入仍是兼容例外，文档不承诺其安全并发。新建对象从 0 开始。还原新建对象不复用归档中的并发版本，旧备份缺版本仍可导入。

版本是布局并发令牌，不是备份内容。只改标题/照片说明时无需递增；删除通过对象不存在拒绝旧写入。不要把新版本只加在 PATCH layout 而漏掉其他位置写入路径。

结构变化使用账号级结构令牌：新增 `journal_layout_state`，每账号一行 `structure_version`。GET journal 在一致性读取事务中返回结构令牌与对象版本/布局，不能分别读取造成混合快照。所有布局/结构写事务先锁定账号结构行，再按确定顺序锁对象；新版请求先检查 expected_structure_version。

创建/删除画布对象、改组/解除分组、折叠/展开、移入手帐或返回画布、导入与还原都会递增结构令牌。新版这些入口同时要求结构令牌；若携带坐标变化，也要求各对象版本。结构变动后旧页面的布局及组操作会得到 409，不再对旧成员列表盲写。legacy 调用仍递增令牌，使新版页面下次保存能检测变化；但不能保证 legacy 请求本身不覆盖新数据，升级说明必须保留这一限制。初次迁移为已有账号建令牌行，新账号在同一建号事务中初始化；缺令牌行视为迁移未完成。

## 保存协调器

新增 `src/journal/canvas/useLayoutPersistence.js`，由 useJournal 持有，每个账号/挂载生命周期独立。统一提供 `editLayout(command)`、`undoLayout()`、`redoLayout()`、`retryLayout()`、`layoutStatus` 和可用性信息，JourneyCanvas 不自行管理历史或回滚。

协调器保存 confirmed 版本/位置、current 期望布局，以及最多一份 inFlight 请求。请求快照创建后不可变；新意图只更新 current。禁止同时发送两份布局请求。

- 成功：只推进该快照的 confirmed；若 current 仍与其不同，状态为未保存，使用返回版本再创建下一快照。旧回执不能把 current 改回快照位置。
- 503/断网/超时：保留 current、历史与原请求快照，进入失败并停止自动发送；不调用 reload 盖掉编辑。重试先原样确认旧快照（利用服务端同值重试），取得版本后再保存 current 与 confirmed 的差异。因此失败后再次编辑也不会以新值猜测旧版本。
- 409：服务端原子冲突响应表示本次请求已经结束且没有写入，清除该 inFlight 快照，保留 current 和失败状态，禁止盲目自动重试；显示“其他页面已修改布局，请重新载入”。提供明确的重新载入操作；它会丢弃本页未保存布局与历史，执行前由产品界面确认。此时可直接读取新基线，不需要不断重试已冲突的请求。
- 401/会话结束：沿用现有 API 代际检查与 abort。卸载清空队列、历史及待重试快照；晚到结果不得更新新账号。保留本机内存编辑与维持账号隔离冲突时，以隔离为先。

短暂“未保存”状态必须真实可观察，不延时伪造；网络请求发出即为保存中。比较 current 与 confirmed 时使用布局内容及版本上下文，不能仅以 Promise resolve 判定整个画布已保存。

## 与现有其他操作的边界

`useJournal.reload` 当前会自动规划避让并写位置，应纳入版本写入审计。存在未确认布局时，后台 reload 不能覆盖 current：先推迟不必要的刷新。显式重新载入走丢弃确认；账号退出走隔离清理。

已经发送的请求不能通过清空客户端队列撤回。显式丢弃/重新载入前，必须先等正在保存的请求完成，或原样重试确认结果不明的快照，然后读取服务端基线；明确的原子 409 响应是已结束的请求，可直接重载。断网期间不能伪装成已安全丢弃服务端操作。账号退出和关闭页面不能等待可靠联网时，说明未确认请求可能已成功，并不承诺撤回。

删除、导入、还原、修改组关系、折叠/展开、移入手帐等作为历史屏障：有未确认布局时先要求保存成功或显式丢弃；操作成功后更新基线并清空历史。失败不丢弃已有历史。应盘点实际入口，不能只在工具栏禁用几个按钮。

后台自动避让也不能在失败编辑上偷偷重排。首批在初次加载且无草稿时完成避让，取得版本确认后才开放历史编辑；后续必要重排作为屏障刷新处理。

## 验证与交付次序

1. 纯历史模型：单次/批量/空命令、撤销重做、新分支、100 条上限、输入快照不可变。
2. 版本迁移和 API：空库/旧库/重复迁移；两账号隔离；整批原子冲突；同值重试不增版本；超时旧写晚到不覆盖新值；其他布局写入口增版本；旧备份不导入并发令牌。
3. 保存协调器：延迟成功不回退新编辑；失败后修改再重试；失败后撤销；确认快照后保存最新差异；409 不盲重试；卸载/退出/账号切换丢弃晚回执；刷新屏障。
4. UI 接入：四种状态、重试按钮、快捷键作用域、拖动只入一条历史、组作为整体、历史屏障和 beforeunload。
5. 将现有 browser 503 用例从“回滚后重拖”改为“保持编辑、点击重试”；保留 M1.2 取消、嵌套分组、折叠等回归。真实 API/E2E 使用隔离数据库，禁止个人库。

本阶段涉及迁移与写协议，发布前运行长期计划中的完整门禁，包括隔离数据库、安全专项、恢复演练及真实 API 浏览器测试。数据库不可用时记录阻塞，不把组件/模拟接口通过作为替代。

## 兼容与回退

新增列不删除现有数据，旧备份继续读取；新客户端依赖版本字段，先迁移后部署前后端，维护窗口关闭旧页面。代码回退可保留新增列，旧版本没有相同并发保证。文档明确变化：失败布局现在保留在内存，刷新会丢失，不能再依赖失败自动跳回旧布局。

## 审查重点

所有坐标写入口是否都更新版本；同值重试是否严格全批匹配；相对照片的撤销边界；任何 reload/CRUD 是否绕过草稿屏障；请求超时后结果不明、重试时又发生编辑或账号切换。
